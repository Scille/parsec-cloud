# Parsec Cloud — Agent Guide

Parsec is a monorepo for a simple, secure, end-to-end encrypted file-sharing cloud app.
This file orients coding agents; each component has its own `README.md` that should be
read when working in that component.

## Components

| Path          | What it is                                             | Read first                          |
| ------------- | ------------------------------------------------------ | ----------------------------------- |
| `cli/`        | CLI client (Rust, `parsec-cli` cargo package)         | `cli/README.md`                     |
| `server/`     | Server (Python, packaged with maturin-bound Rust)      | `server/README.md`, `docs/development/README.md` |
| `client/`     | GUI for web & desktop (Vue 3 + Capacitor + Electron)   | `client/README.md`, `docs/development/README.md` |
| `libparsec/`  | Core business logic in Rust (`libparsec` + `libparsec_*` crates in `libparsec/crates/`) | `libparsec/README.md` |
| `bindings/`   | Generated libparsec bindings (Electron / Web / Android)| `bindings/README.md`                |

Cross-cutting docs live in `docs/development/` (workflow, testbed, adding RPC commands,
adding types with bindings, glossary). Start at `docs/development/README.md`.

## libparsec crate layout

`libparsec/crates/` contains the internal `libparsec_*` crates (folder names drop the
`libparsec_` prefix, e.g. `crates/types` = `libparsec_types`):

- `client`, `client_connection` — the client logic (connection vs. everything else).
- `protocol`, `types`, `serialization_format` — base types (see below).
- `crypto`, `zstd`, `totp`, `account`, `openbao` — algorithm/account helpers.
- `platform_*` — platform-dependent crates (FUSE/WinFSP mountpoint, storage, filesystem,
  async, IPC, …). Crates *without* `platform` in the name are platform-independent.
- `testbed`, `tests_macros`, `tests_lite`, `tests_fixtures` — test helpers. In tests, the
  one-liner is `use libparsec_tests_fixtures::prelude::*;`.

**Rust test convention:** all tests are "unit" tests but live in `tests/unit/`, mirroring the
first-level hierarchy of `src/` (see `libparsec/README.md` FAQ).

### ⚠️ Read the crate README first

Some Rust crates have a `README.md` — **read it before modifying that crate**. In particular:

- `libparsec/crates/protocol/README.md` — protocol commands are defined as `.json5` schemas in
  `libparsec/crates/protocol/schema/<family>/` (families: `authenticated_cmds`, `anonymous_cmds`,
  `invited_cmds`, `tos_cmds`, `anonymous_server_cmds`, `authenticated_account_cmds`) and code is
  generated by macros from `serialization_format`. To add/update a command: bump the API version in
  `libparsec/crates/protocol/src/version.rs`, update the schema with an `introduced_in` attribute,
  and add serialization tests in `libparsec/crates/protocol/tests/` (one per request and per response
  status — enforced at compile time). Serialized test payloads are generated with
  `misc/test_expected_payload_cooker.py` (see the README for the exact workflow).
- `libparsec/crates/types/README.md` — data types (serialized on disk) are `.json5` schemas in
  `libparsec/crates/types/schema/`; same `introduced_in` + tests convention, but **never remove an
  old serialization test when changing a schema** (it proves backward compatibility). Import these
  types as `use libparsec::prelude::*;`.
- `libparsec/crates/serialization_format/README.md` — the proc-macro crate that generates code from
  those schemas.

## Toolchain & commands

The dev environment is assumed to be already configured. Tool versions are pinned by the
following files: `@rust-toolchain.toml` (Rust), `@.nvmrc` (Node), and `uv` for Python
(server venv in `server/.venv`).
- `make.py` at the root wraps common tasks (run `python make.py --help`); notably
  `python make.py run-testbed-server` starts the testbed server.

### Build / test per component

- **libparsec / Rust**: `cargo build --workspace`; tests with `cargo nextest run -p <crate>`
  (e.g. `cargo nextest run -p libparsec_protocol`). CLI: `cargo build/run --package parsec-cli`,
  tests `cargo nextest run --package parsec-cli`.
- **server**: `python ./make.py python-dev-install` once, then `uv --project server run parsec`;
  tests from `server/`: `uv run pytest tests` (options: `-n 4`, `-x`, `-k EXPR`, `--postgresql`).
- **client**: `npm install`; unit tests `npm run test:unit`; lint `npm run lint` (eslint +
  vue-tsc); e2e `npm run test:e2e:headless` (Playwright); web dev `npm run web:open`;
  desktop dev `npm run electron:open`.

### Testbed server

CLI tests, client e2e tests, dev-mode clients, and Rust tests annotated with
`#[parsec_test(testbed = "...", with_server)]` (used in `libparsec_client`,
`libparsec_client_connection`, `libparsec_account`, `libparsec_openbao`, …) all need a
testbed server:

```shell
python make.py run-testbed-server        # or via Docker
export TESTBED_SERVER='parsec3://127.0.0.1:6770?no_ssl=true'
```

The `testbed` crate itself can also spawn one from `TESTBED_SERVER` (or start its own).

## Conventions

- **Commits**: conventional commits (`type(scope): subject`) enforced by commitlint — allowed
  types, scopes and rules are configured in `@.commitlintrc.yml`; check that file for the
  up-to-date list.
- **Changelog**: every user-facing change needs a newsfragment in `newsfragments/`
  named `<issue>.<type>.rst` (types: `feature`, `bugfix`, `misc`, `removal`, …).
  Note: newsfragments will be replaced by `git-cliff` in the near future.
- **Pre-commit**: hooks run on commit via `pre-commit` (or `prek`) — license headers via
  `misc/license_headers.py`, trailing whitespace/EOL fixes, commitlint, ruff, taplo, yamllint,
  cspell, … — see `@.pre-commit-config.yaml`. Run `pre-commit run --all-files` (or
  `prek run --all-files`) before pushing if in doubt.
- **Licensing**: new source files (Python/Rust/Vue/…) need the BUSL-1.1 copyright header — the
  pre-commit hook adds it automatically (`python misc/license_headers.py add`).
- **Branches/PRs**: no strict branch naming convention, but we recommend prefixing the branch
  with the issue ID (e.g. `1234-my-fix`); rebase on `master`, no merge commits; keep PRs small
  and link the issue (see `docs/development/guide-development-workflow.md`).
- **Editor**: respect `@.editorconfig`.
