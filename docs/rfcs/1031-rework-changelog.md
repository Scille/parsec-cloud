# Reworking Changelog Generation for the Project

## Current Process (Starting Point)

The `parsec-cloud` monorepo relies on a well-established release process, which is **not changing** as part of this rework:

- **Release branches** (`releases/X.Y`): Isolate a release from the changes continuously landing of the main branch (`master`).
- **Changelog generation**: `HISTORY.rst` is generated during the release phase, based on fragments manually authored by developers.
- **Pre-releases**: The release branch allows iterating on pre-releases while the version stabilizes.
- **Post-release fixes**: The branch also allows publishing patched versions of the application.
- **Acknowledgment (ACK)**: Once a version is released, a PR (the "ACK PR") is opened from the release branch back to `master` in order to recover:
  - the changelog changes,
  - the manifests (`Cargo.toml`, `pyproject.toml`, `package.json`, …),
  - any fixes developed directly on the release branch.

> Those steps are details here [guide-release-parsec.md (2026-11-02)](https://github.com/Scille/parsec-cloud/blob/3230effe7989b57b7e16f3dc197b21f04f9d5d74/docs/development/guide-release-parsec.md)

## Goals (Target State)

What we want to change is **strictly limited to changelog generation**:

1. **Per component**: one distinct changelog per product (Server, CLI, Web & Electron client).
2. **Automated**: manually creating fragments is a friction point developers easily forget about.
3. **Technical audience**: the changelog is now aimed at developers/integrators, no longer at end users.

Everything else in the process stays unchanged (release branches, pre-releases, ACK).

## Problem Statement

### Determining Which Commits Belong in a Changelog

- **From a release branch (`X.Y.N`, N > 0)**: simple, the tool can rely on the previous tag.
- **From the main branch (`X.Y.0`)**: initially considered harder (no tag on master, ACK commit "slipping in" between unpublished changes).
- **Validated approach**: testing `git-cliff v3.11.0..HEAD` on `master`,
  where `v3.11.0` is the previous release tag and `HEAD` the latest commit on `master` yields a **clean, changelog-ready commit set**.
  The tag range is therefore the primary mechanism;
  the previously considered `git merge-base master releases/X.(Y-1)` and `X.Y.N-ack` tag ideas are dropped as unnecessary.
- Residual detail: ACK commits fall inside the range, but they are excluded from the changelog via the `commit_parsers` `skip` rule (see [The PR ACK duplicated changelog entries](#the-ack-pr-duplicates-changelog-entries)).

### Commit Messages Follow no Convention

- Most tooling relies on **Conventional Commits**.
- To let developers keep commit freedom inside a feature branch, the merge strategy switches from `rebase -> squash`
  - Commit inside the branch stay free-form (`wip`, `fix typo`, …);
  - The final squash commit message = The **PR title** (+ body);
  - Conventional Commits validation therefore targets the **PR title**, not the branch commits.
- Reasoned decision: losing the fine-grained history is **acceptable**:
  - Our PR history contains noise (`fix`, `WIP`, …): squash cleans it up instead of preserving it;
  - `git bisect` already stumbles on partial commits anyway (a commit introducing a breaking change followed by commits propagating it leaves broken intermediate states);
    one atomic commit per PR actually makes bisect more reliable;
  - GitHub keeps PR in its history: archaeology remains possible at any time via the PR and its original commits.

### The ACK PR Duplicates Changelog Entries

- Currently, the ACK PR is merged with **rebase** (multiple commits).
  Commit-based tools would see the same fix twice: once in the changelog of the current release, once in the next one.
- **Solution**: Merge the ACK PR with a **squash** (a single commit).
  Links to the original PRs are preserved in the commit body.
- ACK PR titles are generated by `releaser.py` (e.g. `chore: acknowledge release X.Y.N`) and excluded from the changelog via a `commit_parsers` `skip` rule.

### A Commit Can Affect Several Components

By formatting messages with Conventional Commits, we can declare the commits' **scopes** (e.g. `feat(cli, libparsec): ...`),
letting the tools describe the entry across the relevant changelogs.

## Proposed Workflow: `git-cliff` + Conventional Commits

![`git-cliff`'s mascot moving commits into changelog](https://git-cliff.org/img/git-cliff-anim.gif)

### Attributing Commits to Component: The Scope Decides, the Path Verifies

#### Inclusion by Scope (Source of Truth = Developer Intent):

- Each component holds its own `git-cliff` configuration file in its folder (e.g. `cli/cliff.toml`),
  mirroring the changelog layout. Each file filters on its component's scope via `commit_parsers` (`scope = "cli"`).
- These per-component files **source a shared configuration at the repository root**,
  so global settings (templates, `require_conventional`, shared parser rules) are defined once
- The commit `feat(cli, libparsec) appears in both components' changelogs, regardless of the paths touched.
- A cross-cutting commit without a scope is not lost: a default scope (e.g. `core`/`misc`) can be defined.
- Noise-reduction option: restrict duplication to user-visible `fix`/`feat` types:
  libparsec `chore`/`refactor` entries remain in the libparsec changelog only (configurable in the per-component `commit_parsers`/templates).

#### Verification by Path (CI Guardrail, Asymmetric):

The CI compares the scopes declared in the PR title against the paths actually modified
(`git diff --name-only master..HEAD` mapped component ↔ prefix: `cli/**`, `server/**`, `client/**`, …):

- **Path without scope** → ❌ error (the entry would be missing from a changelog);
- **Scope without path** → ✅ allowed: this constitutes an _impact declaration_.

#### Edge Case: A Libparsec Fix Visible to the CLI/Client:

A `fix(libparsec)` fixing a bug observable by CLI users touches no `cli/**` files.
The developer declares every affected component: `fix(libparsec, cli): ...`
→ the entry appears in both changelogs, although only `libparsec/**` was modified.
Whether a declared impact is legitimate is a matter for human review, not for the CI.

> Path filtering (`--include-path "cli/**"`, repeatable) is available in `git-cliff` but is not retained as the primary mode:
> it ignored developer intent, and a cross-component commit without a scope would appear in no changelog at all.

### For PRs

- **PR titles** are validated against Conventional Commits:
  - An advisory, non-required check when the PR opens (early feedback without blocking);
  - A required check in the Merge Queue: the Merge Queue validates the up-to-date rebased commit immediately
    before it lands on `master`, guaranteeing that no off-convention message reaches the main branch.
- The PR templates pre-fills the `type(scope): ` format, and the `commitlint` configuration is the single source of truth for the list of valid scopes
  (mirroring the component list used by the changelog configurations and the CI guardrail).

### For Releases

The `releaser.py` script is updated: its changelogs generation step is replaced by `git-cliff` invocation, one per component:

```shell
git-cliff --config {component}/cliff.toml --unreleased --tag '{version}' {range}
```

#### Output Format: Markdown, One File Per Component

- Each changelog lives in its component's folder: `cli/CHANGELOG.md`, `server/CHANGELOG.md`, `client/CHANGELOG.md`,
  The file layout matches the component ↔ prefix mapping already used by the CI guardrail.
- Switch from RST to Markdown: our newsfragment regularly contained RST syntax mistakes (notably `inline code` vs _italics_),
  whereas the documentation keeps using RST.
  `git-cliff` natively generates Markdown, removing this source of friction.

#### Existing History

- `HISTORY.rst` is **frozen and renamed `HISTORY-OLD.rst`**: after years of development it contains an extensive history,
  migrating it would deliver little value for a real cost.
  Renaming makes explicit that the file is no longer maintained;
  the new per-component `CHANGELOG.md` files start from the first release of the new process.

## Decision Summary

| Topic | Decision |
| ------------------------------------------ | -------- |
| Determining the commit range               | Tag range from the previous release (validated with `v3.11.0..HEAD`); `merge-base` and ACK tags dropped |
| Attributing a commit to a component        | Hybrid: the scope drives inclusion, the path acts as an asymmetric CI guardrail |
| libparsec fix visible to another component | Impact declaration in the scope: `fix(libparsec, cli)` |
| Merge strategy                             | rebase → squash (all PRs, including ACK PRs) |
| Conventional Commits validation            | On the PR title, via the Merge Queue (required check) + early advisory check |
| Changelog format                           | Markdown, one `CHANGELOG.md` per component, in its folder (`cli/CHANGELOG.md`, …) |
| `git-cliff` configuration                  | One config file per component in its folder, sourcing a shared configuration at the repository root |
| `HISTORY.rst`                              | Frozen and renamed `HISTORY-OLD.rst`; new files start with the new process |
| Validation tool                            | Format: `git-cliff` `require_conventional = true`; policy (allowed scopes/types): `commitlint` `scope-enum`/`type-enum` on the PR title |
| ACK PRs                                    | Title generated by `releaser.py` (`chore: acknowledge release X.Y.N`), excluded from the changelog (`skip`) |

## Alternative Tooling Considered

- [Release drafter](https://github.com/release-drafter/release-drafter):

  Equivalent to _Release please_: Create and maintain a Release PR that can be merged anytime to the main branch to release it.

- [GitHub native notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes):

  GitHub automatic changelog generation, but unclear if it can be used to generate changelog in files, nor if it supports our release workflow.

- [Release please](https://github.com/googleapis/release-please):

  Equivalent to _Release drafter_: Create and maintain a Release PR that can be merged anytime to the main branch to release it.

- [Changesets](https://changesets.dev/):

  It uses a similar concept to our newsfragment but include a front matter to list the impact for each package.

- [Craft](https://craft.sentry.dev/):

  Tool developed by Sentry, not tested but can be used to generate changelogs and more
