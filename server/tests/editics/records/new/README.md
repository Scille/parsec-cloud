# Recorded OnlyOffice scenarios (docker mode, OO 9.3.0 build 138)

Generated by `docs/rfcs/1030-collaborative-editics/oo-protocol-monitor/docker/record.js`
(see `npm run record` in that folder) against the pinned OnlyOffice Document Server
9.3.0 image, with the editors opened as the Parsec test fixtures (Alice / Bob /
Mallory with their device IDs). Every event really happened on the wire in the
listed order: manual-flow only *delays* frames at the MITM proxy to craft the
concurrency, and the export records them at delivery time.

No `cook_record.py` step is needed (the docker harness already uses the right
participant names/IDs); only `sessionId` needs the usual fixup where the record
is parsed.

## Scenario inventory

- `00_auth_alone` — Alice opens the document alone.
- `01_auth_serial` — Alice, then Bob, then Mallory join one after the other.
- `02_auth_concurrent` — Alice, then Bob and Mallory join at the same time (their
  `auth` sends held at the proxy and released back to back, so both auths reach
  the server before Alice's `unLockDocument`). Note the *observed* server
  behavior: only the first joiner (Bob) gets a `waitAuth`; the server resolves
  the document lock optimistically for the second (Mallory authenticates
  directly) — that is what OnlyOffice 9.3.0 really does.
- `10_cursor_serial_{docx,xlsx,pptx}` — the three participants move their
  cursor one after the other (docx: body text + page header; xlsx: cells B3
  then D4; pptx: the slide text shape).
- `13_cursor_concurrent_{docx,xlsx,pptx}` — cursor moves fired in quick
  succession without waiting for the relays (docx: Mallory moves into the
  header while Alice and Bob move in the body).
- `16_cursor_while_auth_{docx,xlsx,pptx}` — Alice moves her cursor while Bob is
  stuck mid-authentication (his `auth` response held at the proxy; Bob receives
  the queued cursor relays only after his auth completes).
- `20_message_alone` / `21_message_serial` / `22_message_concurrent` /
  `23_message_while_auth` — chat messages (alone / one after the other / two
  sends held and released back to back / sent while Bob is mid-auth).
- `30_edit_alone_{docx,xlsx,pptx}` — Alice edits while alone (docx: body text +
  page header; xlsx: cell values committed with Enter; pptx: the slide text).
- `33_edit_serial_{docx,xlsx,pptx}` — Alice, Bob, Mallory edit one after the
  other (in xlsx each participant types its own value: retyping the value
  another participant just saved is a no-op and emits nothing).
- `36_edit_concurrent_{docx,xlsx,pptx}` — the three participants start editing
  at the same time: their `isSaveLock`s are held at the proxy and released back
  to back, so the server sees the three lock requests before granting any save
  lock.
- `39_edit_while_auth_{docx,xlsx,pptx}` — Alice edits while Bob is
  mid-authenticating.

## Notes for review

- The xlsx records also contain `getLock`/`releaseLock` (the spreadsheet cell
  lock flow) — absent from the word/slide records.
- The pptx cursor records have a single logical caret value (`16;…2225`): the
  slide-1 text shape hit zone is tiny and the two click points land on the same
  logical position; the events are real but both targets produce the same
  cursor value.
- The docx header is entered through the editor API (`Asc.editor.GoToHeader(0)`)
  instead of a mouse click: in this Document Server build the grayed header text
  ignores mouse clicks, so the header is not reachable by a plain click. The
  API call is a client-side action producing the very same wire events (cursor
  `14;…682…` and header save changes).
- Participants include Mallory: `test_records.py` currently asserts
  `participant in ("Alice", "Bob")` and only has fixtures for those two — it
  needs extending (Mallory = `de103a11031c00100000000000000000`) before these
  records can be replayed.
